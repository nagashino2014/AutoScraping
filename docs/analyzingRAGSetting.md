## 1. RAG의 정의와 핵심 개념

### 1.1 RAG란?

**RAG (Retrieval-Augmented Generation)**은 대규모 언어 모델(LLM)의 생성 능력에 외부 지식 검색(Retrieval)을 결합한 하이브리드 AI 아키텍처입니다.

```
┌─────────────────────────────────────────────────────────────────────┐
│                         RAG 핵심 공식                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Output = LLM(Query + Retrieved_Context)                          │
│                                                                     │
│   • Query: 사용자 질의                                               │
│   • Retrieved_Context: 벡터 DB에서 검색된 관련 문서 청크             │
│   • LLM: 최종 응답 생성                                              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 RAG가 해결하는 문제

| 문제               | 기존 LLM                                   | RAG 적용 후                         |
| :----------------- | :----------------------------------------- | :---------------------------------- |
| **Hallucination**  | 학습 데이터 외 정보 생성 시 허위 정보 생성 | 실제 문서 기반 응답으로 신뢰성 향상 |
| **최신 정보 부재** | 학습 시점 이후 정보 반영 불가              | 실시간 업데이트된 DB 검색으로 해결  |
| **도메인 특화**    | 일반적 지식만 보유                         | 전문 문서 DB로 도메인 전문성 확보   |
| **근거 제시**      | 응답의 출처 불명확                         | 참조 문서 명시로 투명성 확보        |

### 1.3 EcoMonitor AI에서 RAG의 역할

본 시스템에서 RAG는 환경/에너지 정책 문서에서 **핵심 이슈를 자동 발굴**하고 **심층 분석**을 수행하는 핵심 엔진입니다:

- **데이터 소스**: 환경부, 산업통상자원부 등 정부 기관의 공시/보도자료
- **분석 목표**: 기업에 영향을 미치는 규제 변화, 정책 동향 파악
- **출력물**: 구조화된 모니터링 보고서

## 9. RAG 분석 메뉴 UI 및 기능 구현 청사진

### 9.1 메뉴 구조 변경

#### 기존 구조

```
RAG 분석
├── 데이터 필터링
├── 자동 이슈 발굴
├── 사용자 인터렉션
└── 심층 분석
```

#### 변경 후 구조

```
RAG 분석
├── RAG 분석 (/rag/analysis)           ← 필터링 + 자동 이슈 발굴 통합
├── 사용자 인터랙션 (/rag/interaction)  ← 이슈 검토/수정/재발굴
├── 심층 분석 (/rag/deep-analysis)      ← 심층 분석 수행/결과 확인
└── RAG 설정 (/rag/settings)            ← 모든 RAG 관련 설정
```

### 9.2 각 메뉴별 UI 레이아웃 및 기능

#### 9.2.1 RAG 분석 (`/rag/analysis`)

> **목적**: 분석 대상 데이터 필터링 + 자동 이슈 발굴을 한 화면에서 수행

**주요 기능:**

- 날짜 범위 필터
- 기관/보드/청크 유형 다중 선택 필터
- 실시간 필터링된 청크 수 표시
- 자동 이슈 발굴 실행 (SSE 스트리밍)
- 발굴 진행 상황 프로그레스 바
- 발굴된 이슈 미리보기 카드

**API 엔드포인트:**

```typescript
GET / api / rag / analysis / stats; // 필터링 통계 조회
POST / api / rag / analysis / filter; // 필터 조건 적용
POST / api / rag / discovery / execute; // 이슈 발굴 실행 (SSE)
GET / api / rag / discovery / sessions; // 발굴 세션 목록
```

#### 9.2.2 사용자 인터랙션 (`/rag/interaction`)

> **목적**: 발굴된 이슈 검토, 수정, 재발굴 요청, 최종 선택

**주요 기능:**

- 세션 목록 표시 및 선택
- 이슈 카드 목록 (점수, 요약, 키워드, 출처)
- 이슈 선택/제외/편집 기능
- 일괄 선택/해제
- 점수별/클러스터 크기별 정렬
- 중요도 점수 상세 (법적 강제성, 신규성, 파급력, 국제 동향)

**API 엔드포인트:**

```typescript
GET    /api/rag/discovery/sessions/:id              // 세션 상세 조회
PUT    /api/rag/discovery/sessions/:id              // 세션 업데이트
DELETE /api/rag/discovery/sessions/:id              // 세션 삭제
PUT    /api/rag/discovery/sessions/:id/issues/:id   // 이슈 수정
```

#### 9.2.3 심층 분석 (`/rag/deep-analysis`)

> **목적**: 선택된 핵심 이슈에 대한 심층 분석 수행 및 결과 확인

**주요 기능:**

- 선택된 이슈 목록 표시
- 분석 깊이 설정 (빠른/표준/심층)
- 분석 실행 및 진행 상황 표시
- 단계별 분석 결과 펼침 패널
- 분석 방법 수정 및 재분석
- 보고서 내보내기

**분석 단계:**

1. 데이터 수집 (Retrieval)
2. 초기 분석 (Chain-of-Thought)
3. 심층 추론 (Multi-step Reasoning)
4. 결론 도출 (Synthesis)

**API 엔드포인트:**

```typescript
POST /api/rag/analysis/execute          // 전체 분석 실행 (SSE)
POST /api/rag/analysis/execute/:issueId // 특정 이슈 분석
PUT  /api/rag/analysis/:id/revise       // 분석 결과 수정 요청
GET  /api/rag/analysis/:id/export       // 분석 결과 내보내기
```

#### 9.2.4 RAG 설정 (`/rag/settings`)

> **목적**: RAG 시스템 운용에 필요한 모든 설정 통합 관리

**설정 카테고리:**

| 탭            | 설정 항목                                                |
| :------------ | :------------------------------------------------------- |
| **LLM 모델**  | API 키 관리, 모델 선택, 파라미터 (온도, 토큰), 비용 관리 |

## 12. RAG 분석 기능 고도화 블루프린트 (Phase 2: Precision & Deep Dive)

> **작성일**: 2026-01-30  
> **목적**: 현재 구현된 기본 RAG 분석 시스템을 '실무형 전문가 도구'로 업그레이드하기 위한 기능 및 UI 고도화 방안

### 12.1 중요도 가중치 시스템 고도화 (Dynamic Scoring & Prompting)

현재 단순히 4개의 고정된 슬라이더를 움직이는 것은 LLM에게 모호한 지시를 내리는 것과 같습니다. 이를 **'동적 평가 기준(Dynamic Criteria)'** 시스템으로 변경해야 합니다.

#### 12.1.1 기능적 요구사항

1. **평가 기준(Criteria)의 동적 관리 (CRUD)**

   - **RAG 설정 메뉴**에서 평가 기준을 사용자가 직접 추가/삭제/수정
   - 예: 기본 4개 외에 `산업계 반발 예상도`, `즉시 시행 여부`, `과태료 부과 여부` 등 추가

2. **기준별 '프롬프트 인젝션' 매핑**

   - 단순히 숫자만 전달하는 것이 아니라, 각 기준이 LLM에게 어떤 의미인지 자연어로 정의

   | 항목                 | 설정 예시                                                                                          |
   | -------------------- | -------------------------------------------------------------------------------------------------- |
   | **항목명**           | 법적 강제성                                                                                        |
   | **LLM 지침(Prompt)** | "이 이슈가 기업에게 의무를 부과하거나, 위반 시 제재(과태료, 영업정지 등)가 따르는지 평가하십시오." |
   | **가중치 영향**      | "이 점수가 높을수록 보고서의 '리스크' 섹션에 우선 배치됩니다."                                     |

3. **가중치 시뮬레이션 (Preview)**
   - 설정 메뉴에서 가중치나 프롬프트를 변경했을 때, 샘플 텍스트에 대해 점수가 어떻게 변하는지 테스트 기능

#### 12.1.2 UI 구현 제안

- **발굴 설정 패널**: 고정된 4개 슬라이더 대신, **'평가 기준 추가'** 버튼(+)이 있는 동적 리스트 형태
- **각 슬라이더 옆 툴팁**: 마우스를 올리면 해당 기준이 LLM에게 어떻게 전달되는지(프롬프트 내용) 팝오버로 표시

#### 12.1.3 평가 기준 데이터 구조

```typescript
interface ScoringCriteria {
  id: string;
  label: string; // 화면 표시명
  description: string; // LLM에 주입될 설명
  examples: {
    // 좋은/나쁜 사례 (프롬프트 품질 향상)
    high: string[];
    low: string[];
  };
  weight: number; // 0.0 ~ 1.0
  enabled: boolean;
  calibration?: {
    // 자동 보정(스케일링) 옵션
    minScale: number;
    maxScale: number;
  };
}
```

### 12.2 분석 기간 설정 UI/UX 혁신 (Time-Slicing)

### 12.3 메타데이터 기반 정밀 필터링 (Taxonomy Filtering)

검색 품질(Recall/Precision)을 결정짓는 가장 중요한 요소입니다. 스크래핑 단계부터 데이터 구조를 잡아야 합니다.

#### 12.3.1 데이터 파이프라인 개선 요구사항

1. **스크래핑/전처리 단계**:

   - **DocType 분류**: 본문 내용을 기반으로 `공고`, `보도자료`, `법령안`, `회의록` 등을 분류하는 **LLM 분류기(Classifier)** 필요
   - **Sector 태깅**: 부서명 매핑(1차) + 본문 키워드(PM2.5, 탄소 등)(2차)로 메타데이터 저장

2. **벡터 DB 스키마 확장**:
   ```python
   # ChromaDB 메타데이터 필드 추가
   {
     "doc_type": "press_release | notice | legislation | statistics | etc",
     "sectors": ["air", "water", "waste", "climate", "energy"],
     "source_depth": "headquarters | agency | local",
     "regulation_phase": "proposal | enacted | enforced | audit"
   }
   ```

### 12.4 정밀 발굴을 위한 추가 기능 아이디어

#### 12.4.1 포함/제외 키워드 (Positive/Negative Keywords)

| 기능             | 설명                                                  |
| ---------------- | ----------------------------------------------------- |
| **Must Include** | 이 단어가 포함된 청크는 가중치를 2배로 부여           |
| **Exclude**      | 이 단어가 포함된 청크는 아예 검색/클러스터링에서 배제 |

- **UI**: 태그 입력창 형태 (파란색 태그: 포함 / 빨간색 태그: 제외)

#### 12.4.2 클러스터링 민감도 (Semantic Sensitivity)

| 설정                 | 효과                                                             |
| -------------------- | ---------------------------------------------------------------- |
| **느슨하게(Broad)**  | "탄소중립"이라는 큰 주제로 묶음                                  |
| **엄격하게(Strict)** | "탄소배출권 가격", "탄소국경세", "RE100"을 모두 다른 이슈로 분리 |

- **UI**: "이슈 응집도" 슬라이더 (Broad <-> Strict)

#### 12.4.3 출처 신뢰도 가중치 (Source Reliability)

- 기관별/게시판별로 중요도 등급(Tier 1, 2, 3)을 매겨 점수 산정 시 반영
- **UI**: 기관 필터 옆에 별점(★)이나 중요도 토글 스위치 배치

#### 12.4.4 관심 기업/물질 엔티티 필터 (Named Entity Filter)

- 특정 기업(예: 삼성전자, SK하이닉스)이나 특정 화학물질에 대한 이슈만 필터링
- 미리 정의된 관심 엔티티 리스트를 선택하여 필터링

## 13. 통합환경허가 사업장 맞춤형 기능 (Client-Specific RAG)

> **목적**: 통합환경허가 대상 사업장(발전, 철강/제철, 화학, 전자, 반도체, 폐기물소각 등)을 주 고객으로 하는 모니터링 보고서 플랫폼에서, 클라이언트의 업종/사업장 규모/적용 대상 법률에 대한 정밀한 매칭 설정

### 13.1 고객 페르소나(Client Persona) 설정

이슈 발굴 전 분석 대상 사업장의 정체성을 명확히 정의. 이 정보는 RAG의 시스템 프롬프트에 주입되어 AI가 문서를 해석하는 관점을 결정합니다.

#### 13.1.1 업종(Industry) 선택 및 공정 태그

| 업종           | 세부 공정 예시                                   |
| -------------- | ------------------------------------------------ |
| **철강/제철**  | [소결공정], [코크스공정], [제강공정], [압연공정] |
| **반도체**     | [식각공정], [세정공정], [CMP], [유기용제 사용]   |
| **발전**       | [연소], [탈황], [탈질], [집진]                   |
| **화학**       | [합성], [증류], [건조], [포장]                   |
| **폐기물소각** | [연소], [배가스처리], [잔재물처리]               |

**효과**: "질소산화물(NOx) 저감"이라는 이슈가 발굴되었을 때, 이를 일반적인 내용이 아닌 "소결로 SCR 설비 강화 필요성"으로 해석 가능

#### 13.1.2 사업장 규모 및 입지

| 설정 항목        | 옵션 예시                                  |
| ---------------- | ------------------------------------------ |
| **대기관리권역** | 수도권, 중부권, 남부권, 동남권 등          |
| **사업장 종별**  | 1종~5종                                    |
| **특수지역**     | 수질오염총량관리지역, 배출권거래제 대상 등 |

**효과**: 특정 권역에만 적용되는 '대기오염물질 총량관리제' 관련 고시에 해당 권역 사업장에게만 가중치 부여

### 13.3 법적 적용 범위 설정 (Legal Scope Configuration)

#### 13.3.1 적용 법령 매트릭스

| 카테고리          | 법령 예시                                  | 설정 옵션      |
| ----------------- | ------------------------------------------ | -------------- |

| **매체별 개별법** | 대기환경보전법, 물환경보전법, 폐기물관리법 | 관심/일반/무시 |
| **안전/보건**     | 중대재해처벌법, 화학물질관리법             | 관심/일반/무시 |
| **에너지/탄소**   | 탄소중립기본법, 배출권거래법               | 관심/일반/무시 |

```
[입법예고(대응 가능 단계)] → [공포(확정 단계)] → [시행(적용 단계)] → [단속/점검(리스크 단계)]
```

**활용**: 컨설팅 목적상 **'입법예고'** 단계의 문서에 가중치를 두어, 고객사가 의견을 제출하거나 설비를 미리 준비할 수 있도록 유도

### 13.4 컨설팅 로직 (프롬프트·가중치·분석 체인)

#### 13.4.1 BAT(최적가용기법) 기준서 연동 분석

- **RAG 설정**: "BAT 기준서 변경 사항 감지 모드" 활성화
- **로직**: 환경부의 '최적가용기법 기준서' 개정 관련 내용이 나오면, 기존 공정 기술과 비교하여 설비 교체 필요성 분석

#### 13.4.2 리스크 유형별 가중치 (Risk Scoring)

| 리스크 유형          | 설명                                                    |
| -------------------- | ------------------------------------------------------- |
| **Cost Impact**      | 배출부과금, 과태료, 설비 투자비 증가 요인               |
| **Operation Impact** | 조업 정지, 허가 취소, 공정 가동률 조정 요인             |
| **Admin Impact**     | 보고서 제출 주기 변경, 측정 횟수 증가 등 행정 부담 요인 |

## 14. 고객 페르소나 및 컨설팅 로직 보강 (Advanced Features)

### 14.1 "공정/설비-배출구" 수준의 구조화

| 레벨                     | 구성요소                                           | 예시         |
| ------------------------ | -------------------------------------------------- | ------------ |
| **설비(Emission Unit)**  | 소결로, 보일러, 소각로, 스크러버, SCR 등           | -            |
| **배출구(Stack/Outlet)** | 배출구별 오염물질, 배출량, 방지시설, 측정기기 여부 | TMS/자가측정 |

**효과**: 이슈가 "사업장 전체"가 아니라 "특정 배출구/공정"에 직접 매칭되어 대응방안이 구체화됨

### 14.2 "허가조건"과의 매칭

사업장별 통합허가서에 들어가는 **허가조건 항목**을 구조화:

- 모니터링 주기
- 한계배출기준
- BAT-AEL
- 운영조건

법령/고시/기준서 변경이 나오면:

- **허가조건 변경 가능성(High/Med/Low)** 점수화
- **변경 시 필요한 조치** 자동 후보 생성 (측정 주기 변경, 설비 증설, 운영조건 변경)

### 14.3 "규제 성숙도/준수 수준" 프로파일

| 항목           | 설명                               |
| -------------- | ---------------------------------- |
| 현재 준수 수준 | 여유율/초과이력/개선계획 보유 여부 |
| 최근 행정처분  | 12~24개월 내 개선명령/점검 결과    |

**효과**: 동일한 규제라도 "위험 사업장"에 더 높은 우선순위를 부여

### 14.4 물질 그룹/규제 목록 기반 태깅

단일 물질(CAS)뿐 아니라 **그룹** 단위 설정:

- PFAS군
- 특정수질유해물질군
- VOC군
- 유해대기오염물질(HAPs)

문서에서 물질명이 직접 안 나와도 **동의어/약어/상품명**까지 매칭 (사전/LLM 하이브리드)

### 14.5 단위/기준치 변화 탐지

| 탐지 대상      | 설명               |
| -------------- | ------------------ |
| 단위 변환      | "mg/L→μg/L"        |
| 기준 강화/완화 | 수치 변경          |
| 측정방법 변경  | 공정시험 변경      |
| 산정방법 변경  | 배출량 계산식 변경 |

텍스트에서 **수치(숫자), 단위, 대상 공정/시설**을 추출하는 룰+모델 혼합(정규식 + NER)

### 14.6 법령 변경 단계 외 "리스크 유형" 분류

| 유형                       | 설명                               |
| -------------------------- | ---------------------------------- |
| **의무부과(Compliance)**   | 새로운 의무 발생                   |
| **보고·공시(Disclosure)**  | 공시 의무 변경                     |
| **경제수단**               | 부과금·배출권 변경                 |
| **단속·점검(Enforcement)** | 점검 강화                          |
| **지원·인센티브(Subsidy)** | 보조금/지원사업 (투자비 절감 기회) |

### 14.7 '점수'만 말고 "액션(조치)"까지 산출하는 구조

이슈 카드가 다음 구조를 갖도록 설계:

```typescript
interface IssueActionCard {
  obligation: string; // 무엇을 해야 하는가
  deadline: string; // 언제까지
  evidence: {
    // 근거
    document: string;
    article: string;
    page: number;
  };
  impact: {
    // 영향
    cost: "high" | "medium" | "low";
    operation: "high" | "medium" | "low";
    admin: "high" | "medium" | "low";
    reputation: "high" | "medium" | "low";
  };
  actions: {
    // 대응
    immediate: string[];
    shortTerm: string[];
    midTerm: string[];
    longTerm: string[];
  };
  owner: string; // 담당부서 (환경/안전/생산/법무/구매 등 추천)
}
```

### 14.8 업종-규제 지식 그래프 구축

| 구성요소 | 예시                                                    |
| -------- | ------------------------------------------------------- |
| **노드** | 업종/공정/시설/오염원/물질/법령/고시/허가조건/BAT 항목  |
| **엣지** | "적용된다", "관련된다", "대체/방지시설이다", "측정한다" |

발굴된 문서가 들어오면:

- 그래프에서 **영향 경로(path)**를 찾아 "왜 중요한지" 설명 가능
- 사용자에게 "우리 공장 공정 X → 법령 Y 변경 영향"으로 보여주기 쉬움

### 14.9 리스크 시뮬레이션 (비용/조업/행정)

| 영향 유형           | 추정 항목                                  |
| ------------------- | ------------------------------------------ |
| **설비 투자 CAPEX** | 범주 추정 (정확한 금액이 아니라 등급/범위) |
| **운영비 OPEX**     | 약품/전력/폐기물 처리 비용 변화            |
| **행정 부담**       | 보고서/측정 빈도/검사 비용                 |

"영향도"를 다차원으로 표현: 비용/조업/법적리스크/기간

### 14.10 데이터 품질 & 신뢰성 설정

| 항목                      | 설명                                    |
| ------------------------- | --------------------------------------- |

## 17. RAG 핵심 원리: LLM의 역할과 작동 방식

> **목적**: RAG 아키텍처에서 LLM이 실제로 어떻게 작업을 수행하는지에 대한 정확한 이해

### 17.1 흔한 오해 바로잡기

| 오해                                | 실제                                      |
| ----------------------------------- | ----------------------------------------- |
| LLM이 벡터 DB 전체를 **"학습"**한다 | LLM은 벡터 DB를 **전혀 학습하지 않음**    |
| 질문 시마다 DB 전체를 읽는다        | **관련된 소수의 청크만** 검색해서 전달    |
| 막대한 토큰 비용이 발생한다         | 검색된 Top-K 청크만 처리하므로 **저비용** |

**핵심**: LLM은 "검색된 소수의 문서"만 읽고 답변합니다. 벡터 DB 전체를 학습하거나 읽지 않습니다.

### 17.2 RAG 작동 순서 (실제 흐름)

```
사용자 질문: "2026년 대기오염물질 배출기준 강화 내용은?"
                    │
                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Step 1: 질문 → 벡터 변환 (임베딩)                                   │
│  ─────────────────────────────────                                  │

│                                                                     │
│  ⚡ 이 과정은 LLM이 아닌 "벡터 검색 엔진"이 수행                      │

                    │
                    ▼
┌─────────────────────────────────────────────────────────────────────┐
```

### 17.3 비용이 저렴한 이유

```
┌─────────────────────────────────────────────────────────────────────┐
│                        토큰 소모 비교                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ❌ 만약 DB 전체를 매번 읽는다면:                                    │
│  ────────────────────────────────                                   │
│  400만 청크 × 2,500자 = 100억 자 ≈ 40억 토큰                        │
│  GPT-4o-mini 기준: 40억 × $0.15/1M = $600 (1회 질문당!)             │
│                                                                     │
│  ✅ 실제 RAG (검색 후 상위 K개만):                                   │
│  ──────────────────────────────────                                 │
│  상위 20개 청크 × 2,500자 = 50,000자 ≈ 20,000 토큰                  │
│  GPT-4o-mini 기준: 20,000 × $0.15/1M = $0.003 (1회 질문당!)         │
│                                                                     │
│  💡 비용 차이: 약 200,000배                                          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 17.4 RAG 핵심 용어 정리

| 용어           | 의미                           | 담당                    |
| -------------- | ------------------------------ | ----------------------- |
| **Embedding**  | 텍스트를 숫자 벡터로 변환      | 임베딩 모델 (bge-m3 등) |
| **Vector DB**  | 벡터를 저장하고 유사도 검색    | ChromaDB/Pinecone       |
| **Retrieval**  | 질문과 유사한 청크 Top-K 추출  | 벡터 DB 엔진            |
| **Generation** | 검색된 컨텍스트 기반 답변 생성 | LLM (GPT/Claude)        |

### 17.5 도서관 비유

```
📚 도서관 비유로 이해하기:

❌ 잘못된 이해:
"사서(LLM)가 도서관의 모든 책을 외운 뒤, 질문에 답한다"

✅ 실제 RAG:
1. 사용자가 "환경 규제"에 대해 질문
2. 검색 시스템이 도서관에서 관련 책 5권을 찾아옴 (Retrieval)
3. 사서(LLM)는 그 5권만 읽고 답변함 (Generation)

→ 사서는 도서관 전체를 외우지 않음
→ 검색 시스템이 관련 자료만 빠르게 찾아줌
```

#### 18.3.2 Re-ranking (2단계 정밀 순위화)

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Re-ranking Pipeline                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Stage 1: 빠른 검색 (Bi-Encoder)                                     │
│  ────────────────────────────────                                   │
│  벡터 DB에서 Top-100 청크 빠르게 추출                                │
│  (코사인 유사도, 밀리초 단위)                                        │
│                                                                     │
│           │                                                         │
│           ▼                                                         │
│                                                                     │
│  Stage 2: 정밀 재순위화 (Cross-Encoder)                              │
│  ──────────────────────────────────────                             │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                                                              │   │
│  │  Cross-Encoder 모델 (예: ms-marco-MiniLM)                   │   │
│  │                                                              │   │
│  │  입력: [질문] + [후보 청크] 쌍으로 직접 비교                 │   │
│  │                                                              │   │
│  │  "NOx 배출기준 강화" + "청크1" → 관련성 점수: 0.92          │   │
│  │  "NOx 배출기준 강화" + "청크2" → 관련성 점수: 0.45          │   │
│  │  "NOx 배출기준 강화" + "청크3" → 관련성 점수: 0.88          │   │
│  │  ...                                                         │   │
│  │                                                              │   │
│  │  → 점수순 재정렬 후 Top-20만 LLM에 전달                      │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  💡 Bi-Encoder: 빠르지만 덜 정확 (독립적 임베딩 비교)               │
│  💡 Cross-Encoder: 느리지만 매우 정확 (쌍으로 직접 비교)            │
│  💡 조합: 1단계에서 후보군 축소 → 2단계에서 정밀 선별               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 18.3.3 Query Decomposition (질문 분해)

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Query Decomposition                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  원본 질문 (복잡):                                                   │
│  "통합허가 대상 철강 사업장의 NOx 배출기준이 강화되면                │
│   어떤 설비 투자가 필요하고, 관련 지원제도는 있는가?"                │
│                                                                     │
│           │                                                         │
│           ▼  LLM이 질문 분해                                        │
│                                                                     │
│  Sub-Q 1: "철강 사업장 NOx 배출허용기준 변경 내역"                   │
│  Sub-Q 2: "NOx 저감 설비 종류와 투자비용"                           │
│  Sub-Q 3: "대기오염방지시설 투자 지원제도"                          │
│  Sub-Q 4: "통합허가 BAT 기준서 NOx 관련 내용"                       │
│                                                                     │
│           │                                                         │
│           ▼  각 Sub-Q로 별도 검색                                   │
│                                                                     │
│  Sub-Q 1 → 검색 → 청크 A1, A2, A3                                   │
│  Sub-Q 2 → 검색 → 청크 B1, B2, B3                                   │
│  Sub-Q 3 → 검색 → 청크 C1, C2                                       │
│  Sub-Q 4 → 검색 → 청크 D1, D2, D3, D4                               │
│                                                                     │
│           │                                                         │
│           ▼  통합하여 LLM에 전달                                    │
│                                                                     │
│  💡 복잡한 질문 하나로 검색 → 관련 없는 결과 다수                    │
│  💡 분해 후 검색 → 각 측면에 정확히 맞는 문서 수집                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 18.3.4 Self-Query (LLM 자가 필터링)

```python
# LLM이 사용자 질문을 분석하여 메타데이터 필터를 자동 생성

사용자: "2025년 이후 환경부에서 발표한 대기 분야 법령안"

LLM 자가 분석 결과:
{
  "semantic_query": "대기오염 관련 법령 개정안",
  "metadata_filter": {
    "published_date": { "$gte": "2025-01-01" },
    "organization": "환경부",
    "sector": "air",
    "doc_type": ["legislation", "notice"]
  }
}

→ 벡터 검색 전에 메타데이터로 후보군을 대폭 축소
→ 관련 없는 문서가 섞일 확률 감소
```

## 20. Retrieval 품질 향상 전략 상세 (Advanced Retrieval Strategies)

> **목적**: 벡터 검색(Bi-Encoder)의 근본적 한계를 극복하고 검색 정확도를 획기적으로 향상시키기 위한 상세 구현 가이드

### 20.1 Bi-Encoder의 근본적 한계

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    Bi-Encoder의 구조적 한계점                                    │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  질문: "2026년 철강업 NOx 배출기준 강화 영향"                                     │
│                                                                                 │
│  문제 1: 어휘 불일치 (Vocabulary Mismatch)                                       │
│  ────────────────────────────────────────                                       │
│  • 질문에 "NOx" → 문서에 "질소산화물"                                            │
```

#### 20.2.3 Cross-Encoder 구현 코드

```python
# backend/app/reranker.py

"""
Cross-Encoder 기반 Reranking 모듈

사용 모델:
- BAAI/bge-reranker-v2-m3 (다국어, 한국어 지원 우수)
- BAAI/bge-reranker-large (영어 중심, 성능 최고)
"""

from typing import List, Dict, Any, Tuple
from dataclasses import dataclass
import torch

# 모델 캐싱을 위한 전역 변수
_reranker_model = None
_reranker_tokenizer = None


@dataclass
class RerankedResult:
    """리랭킹 결과"""
    chunk: Dict[str, Any]
    original_score: float      # 벡터 유사도 점수
    rerank_score: float        # Cross-Encoder 점수
    rank_change: int           # 순위 변동 (양수: 상승, 음수: 하락)


def load_reranker(model_name: str = "BAAI/bge-reranker-v2-m3"):
    """Reranker 모델 로드 (최초 1회만)"""
    global _reranker_model, _reranker_tokenizer

    if _reranker_model is not None:
        return _reranker_model, _reranker_tokenizer

    from transformers import AutoModelForSequenceClassification, AutoTokenizer

    print(f"[Reranker] Loading model: {model_name}")

    _reranker_tokenizer = AutoTokenizer.from_pretrained(model_name)
    _reranker_model = AutoModelForSequenceClassification.from_pretrained(model_name)

    if torch.cuda.is_available():
        _reranker_model = _reranker_model.cuda()
        print("[Reranker] Using GPU")

    _reranker_model.eval()
    return _reranker_model, _reranker_tokenizer


def compute_rerank_scores(
    query: str,
    documents: List[str],
    model_name: str = "BAAI/bge-reranker-v2-m3",
    batch_size: int = 8,
    max_length: int = 512
) -> List[float]:
    """Cross-Encoder로 Query-Document 쌍의 관련성 점수 계산"""
    model, tokenizer = load_reranker(model_name)

    scores = []

    for i in range(0, len(documents), batch_size):
        batch_docs = documents[i:i + batch_size]
        pairs = [[query, doc] for doc in batch_docs]

        with torch.no_grad():
            inputs = tokenizer(
                pairs,
                padding=True,
                truncation=True,
                max_length=max_length,
                return_tensors="pt"
            )

            if torch.cuda.is_available():
                inputs = {k: v.cuda() for k, v in inputs.items()}

            outputs = model(**inputs)
            batch_scores = torch.sigmoid(outputs.logits.squeeze(-1)).cpu().tolist()

            if isinstance(batch_scores, float):
                batch_scores = [batch_scores]

            scores.extend(batch_scores)

    return scores


def rerank_chunks(
    query: str,
    chunks: List[Dict[str, Any]],
    top_n: int = 10,
    model_name: str = "BAAI/bge-reranker-v2-m3"
) -> List[RerankedResult]:
    """청크 리스트를 Cross-Encoder로 리랭킹"""
    if not chunks:
        return []

    documents = [chunk.get("content", "")[:2000] for chunk in chunks]
    rerank_scores = compute_rerank_scores(query, documents, model_name)

    scored_chunks = list(zip(chunks, rerank_scores, range(len(chunks))))
    scored_chunks.sort(key=lambda x: x[1], reverse=True)

    results = []
    for new_rank, (chunk, score, original_rank) in enumerate(scored_chunks[:top_n]):
        results.append(RerankedResult(
            chunk=chunk,
            original_score=chunk.get("score", 0.0),
            rerank_score=score,
            rank_change=original_rank - new_rank
        ))

    return results
```

```python
# backend/app/hybrid_search.py

"""
Hybrid Search 모듈 - Semantic (벡터) + Lexical (BM25) 검색 결합
"""

from typing import List, Dict, Any, Tuple
from rank_bm25 import BM25Okapi
import re
from collections import defaultdict


class HybridSearcher:
    """하이브리드 검색기"""

    def __init__(
        self,
        semantic_weight: float = 0.5,
        lexical_weight: float = 0.5,
        rrf_k: int = 60
    ):
        self.semantic_weight = semantic_weight
        self.lexical_weight = lexical_weight
        self.rrf_k = rrf_k
        self.bm25 = None
        self.corpus = []
        self.chunk_map = {}

    def _tokenize_korean(self, text: str) -> List[str]:
        """한국어 토크나이징"""
        tokens = re.findall(r'[가-힣]+|[a-zA-Z]+|[0-9]+', text.lower())
        return [t for t in tokens if len(t) >= 2]

    def index_chunks(self, chunks: List[Dict[str, Any]]):
        """청크를 BM25 인덱스에 추가"""
        self.corpus = []
        self.chunk_map = {}

        for i, chunk in enumerate(chunks):
            content = chunk.get("content", "")
            tokens = self._tokenize_korean(content)
            self.corpus.append(tokens)
            self.chunk_map[i] = chunk

        self.bm25 = BM25Okapi(self.corpus)

    def reciprocal_rank_fusion(
        self,
        semantic_results: List[Tuple[int, float]],
        lexical_results: List[Tuple[int, float]],
        top_k: int = 50
    ) -> List[Tuple[int, float]]:
        """Reciprocal Rank Fusion (RRF)"""
        rrf_scores = defaultdict(float)

        for rank, (idx, _) in enumerate(semantic_results):
            rrf_scores[idx] += self.semantic_weight / (self.rrf_k + rank + 1)

        for rank, (idx, _) in enumerate(lexical_results):
            rrf_scores[idx] += self.lexical_weight / (self.rrf_k + rank + 1)

        sorted_results = sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True)
        return sorted_results[:top_k]

    def hybrid_search(
        self,
        query: str,
        semantic_results: List[Dict[str, Any]],
        top_k: int = 50
    ) -> List[Dict[str, Any]]:
        """하이브리드 검색 수행"""
        self.index_chunks(semantic_results)

        # Semantic 결과
        semantic_indexed = [(i, chunk.get("score", 0.0)) for i, chunk in enumerate(semantic_results)]

        # BM25 검색
        query_tokens = self._tokenize_korean(query)
        bm25_scores = self.bm25.get_scores(query_tokens)
        lexical_results = sorted(enumerate(bm25_scores), key=lambda x: x[1], reverse=True)

        # RRF 융합
        fused = self.reciprocal_rank_fusion(semantic_indexed, lexical_results, top_k)

        results = []
        for idx, rrf_score in fused:
            chunk = self.chunk_map[idx].copy()
            chunk["hybrid_score"] = rrf_score
            results.append(chunk)

        return results
```

```python
async def multi_query_retrieval(
    queries: List[str],
    vector_search_fn,
    top_k_per_query: int = 30,
    max_total: int = 80
) -> List[Dict[str, Any]]:
    """여러 질의로 검색 후 결과 통합"""
    all_results = {}
    query_sources = {}

    for query in queries:
        results = await vector_search_fn(query, top_k=top_k_per_query)

        for chunk in results:
            chunk_id = chunk.get("id") or hash(chunk.get("content", "")[:100])

            if chunk_id not in all_results:
                all_results[chunk_id] = chunk
                query_sources[chunk_id] = [query]
            else:
                query_sources[chunk_id].append(query)
                # 여러 질의에서 검색된 경우 점수 보너스
                all_results[chunk_id]["score"] += 0.1

    # 여러 질의에서 나온 문서 우선 정렬
    sorted_results = sorted(
        all_results.values(),
        key=lambda x: (len(query_sources.get(x.get("id"), [])), x.get("score", 0)),
        reverse=True
    )

    return sorted_results[:max_total]
```

```python
5. 시행일자나 적용시기 포함

문서:"""

    # LLM API 호출하여 가상 문서 생성
    # ... (구현 생략)

    return hypothetical_document


async def hyde_search(
    query: str,
    embedding_fn,
    vector_search_fn,
    llm_api_key: str,
    top_k: int = 50,
    num_hypothetical: int = 3
) -> List[Dict[str, Any]]:
    """HyDE 방식 검색"""
    all_results = {}

    doc_types = ["정책 문서", "보도자료", "연구보고서"]

    for i in range(num_hypothetical):
        doc_type = doc_types[i % len(doc_types)]

        # 가상 문서 생성
        hypo_doc = await generate_hypothetical_document(query, llm_api_key, document_type=doc_type)

        # 가상 문서 임베딩
        hypo_embedding = await embedding_fn(hypo_doc)

        # 임베딩으로 검색
        results = await vector_search_fn(embedding=hypo_embedding, top_k=top_k)

        # 결과 통합
        for chunk in results:
            chunk_id = chunk.get("id") or hash(chunk.get("content", "")[:100])
            if chunk_id not in all_results:
                all_results[chunk_id] = chunk
                all_results[chunk_id]["hyde_match_count"] = 1
            else:
                all_results[chunk_id]["hyde_match_count"] += 1

    sorted_results = sorted(
        all_results.values(),
        key=lambda x: (x.get("hyde_match_count", 0), x.get("score", 0)),
        reverse=True
    )

    return sorted_results[:top_k]
```

```python
# backend/app/advanced_retrieval.py

"""
Advanced RAG Retrieval Pipeline
- Query Expansion + HyDE + Hybrid Search + Reranking 통합
"""

from typing import List, Dict, Any, Optional
from dataclasses import dataclass
from enum import Enum


class RetrievalStrategy(Enum):
    BASIC = "basic"           # 단순 벡터 검색
    HYBRID = "hybrid"         # 벡터 + BM25
    ADVANCED = "advanced"     # 전체 파이프라인


@dataclass
class RetrievalConfig:
    """검색 설정"""
    strategy: RetrievalStrategy = RetrievalStrategy.ADVANCED

    # Direct Search
    direct_top_k: int = 50

    # Query Expansion
    enable_query_expansion: bool = True
    num_expanded_queries: int = 5
    expansion_top_k: int = 30

    # HyDE
    enable_hyde: bool = True
    num_hypothetical_docs: int = 3
    hyde_top_k: int = 50

    # Hybrid Search
    enable_hybrid: bool = True
    semantic_weight: float = 0.5
    lexical_weight: float = 0.5

    # Reranking
    enable_reranking: bool = True
    rerank_top_n: int = 15
    reranker_model: str = "BAAI/bge-reranker-v2-m3"


class AdvancedRetriever:
    """고급 검색 파이프라인"""

    def __init__(
        self,
        vector_db,
        embedding_model,
        llm_api_key: str,
        config: Optional[RetrievalConfig] = None
    ):
        self.vector_db = vector_db
        self.embedding_model = embedding_model
        self.llm_api_key = llm_api_key
        self.config = config or RetrievalConfig()

        self.hybrid_searcher = HybridSearcher(
            semantic_weight=self.config.semantic_weight,
            lexical_weight=self.config.lexical_weight
        )

    async def retrieve(
        self,
        query: str,
        filters: Optional[Dict[str, Any]] = None
    ) -> List[Dict[str, Any]]:
        """고급 검색 파이프라인 실행"""
        all_candidates = {}
        retrieval_sources = {}

        # ========================================
        # Stage 1: Multi-Source Retrieval
        # ========================================

        # 1-A: Direct Vector Search
        direct_results = await self._vector_search(query, self.config.direct_top_k, filters)
        self._merge_results(all_candidates, retrieval_sources, direct_results, "direct")

        # 1-B: Query Expansion Search
        if self.config.enable_query_expansion:
            expanded_queries = await expand_query_with_llm(
                query, self.llm_api_key,
                num_expansions=self.config.num_expanded_queries
            )

            for exp_query in expanded_queries[1:]:
                exp_results = await self._vector_search(exp_query, self.config.expansion_top_k, filters)
                self._merge_results(all_candidates, retrieval_sources, exp_results, f"expanded")

        # 1-C: HyDE Search
        if self.config.enable_hyde:
            hyde_results = await hyde_search(
                query,
                embedding_fn=self._embed_text,
                vector_search_fn=self._vector_search_by_embedding,
                llm_api_key=self.llm_api_key,
                top_k=self.config.hyde_top_k,
                num_hypothetical=self.config.num_hypothetical_docs
            )
            self._merge_results(all_candidates, retrieval_sources, hyde_results, "hyde")

        candidates = list(all_candidates.values())
        print(f"[Retrieval] Stage 1 완료: {len(candidates)}개 후보")

        # ========================================
        # Stage 2: Hybrid Search Refinement
        # ========================================

        if self.config.enable_hybrid and len(candidates) > 20:
            candidates = self.hybrid_searcher.hybrid_search(
                query, candidates, top_k=min(80, len(candidates))
            )
            print(f"[Retrieval] Stage 2 (Hybrid) 완료: {len(candidates)}개")

        # ========================================
        # Stage 3: Cross-Encoder Reranking
        # ========================================

        if self.config.enable_reranking and len(candidates) > 5:
            from .reranker import rerank_chunks

            reranked = rerank_chunks(
                query, candidates,
                top_n=self.config.rerank_top_n,
                model_name=self.config.reranker_model
            )
            candidates = [r.chunk for r in reranked]

            promoted = sum(1 for r in reranked if r.rank_change > 10)
            if promoted > 0:
                print(f"[Retrieval] Reranking: {promoted}개 문서 크게 상승 (>10 ranks)")

        print(f"[Retrieval] 최종: {len(candidates)}개 고품질 문서")

        return candidates
```
