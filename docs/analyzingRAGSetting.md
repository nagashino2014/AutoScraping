## 1. RAG의 정의와 핵심 개념

### 1.1 RAG란?

**RAG (Retrieval-Augmented Generation)**은 대규모 언어 모델(LLM)의 생성 능력에 외부 지식 검색(Retrieval)을 결합한 하이브리드 AI 아키텍처입니다.

```
┌─────────────────────────────────────────────────────────────────────┐
│                         RAG 핵심 공식                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Output = LLM(Query + Retrieved_Context)                          │
│                                                                     │
│   • Query: 사용자 질의                                               │
│   • Retrieved_Context: 벡터 DB에서 검색된 관련 문서 청크             │
│   • LLM: 최종 응답 생성                                              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 RAG가 해결하는 문제

| 문제               | 기존 LLM                                   | RAG 적용 후                         |
| :----------------- | :----------------------------------------- | :---------------------------------- |
| **Hallucination**  | 학습 데이터 외 정보 생성 시 허위 정보 생성 | 실제 문서 기반 응답으로 신뢰성 향상 |
| **최신 정보 부재** | 학습 시점 이후 정보 반영 불가              | 실시간 업데이트된 DB 검색으로 해결  |
| **도메인 특화**    | 일반적 지식만 보유                         | 전문 문서 DB로 도메인 전문성 확보   |
| **근거 제시**      | 응답의 출처 불명확                         | 참조 문서 명시로 투명성 확보        |

### 1.3 EcoMonitor AI에서 RAG의 역할

본 시스템에서 RAG는 환경/에너지 정책 문서에서 **핵심 이슈를 자동 발굴**하고 **심층 분석**을 수행하는 핵심 엔진입니다:

- **데이터 소스**: 환경부, 산업통상자원부 등 정부 기관의 공시/보도자료
- **분석 목표**: 기업에 영향을 미치는 규제 변화, 정책 동향 파악
- **출력물**: 구조화된 모니터링 보고서

## 9. RAG 분석 메뉴 UI 및 기능 구현 청사진

### 9.1 메뉴 구조 변경

#### 기존 구조

```
RAG 분석
├── 데이터 필터링
├── 자동 이슈 발굴
├── 사용자 인터렉션
└── 심층 분석
```

#### 변경 후 구조

```
RAG 분석
├── RAG 분석 (/rag/analysis)           ← 필터링 + 자동 이슈 발굴 통합
├── 사용자 인터랙션 (/rag/interaction)  ← 이슈 검토/수정/재발굴
├── 심층 분석 (/rag/deep-analysis)      ← 심층 분석 수행/결과 확인
└── RAG 설정 (/rag/settings)            ← 모든 RAG 관련 설정
```

### 9.2 각 메뉴별 UI 레이아웃 및 기능

#### 9.2.1 RAG 분석 (`/rag/analysis`)

> **목적**: 분석 대상 데이터 필터링 + 자동 이슈 발굴을 한 화면에서 수행

**주요 기능:**

- 날짜 범위 필터
- 기관/보드/청크 유형 다중 선택 필터
- 실시간 필터링된 청크 수 표시
- 자동 이슈 발굴 실행 (SSE 스트리밍)
- 발굴 진행 상황 프로그레스 바
- 발굴된 이슈 미리보기 카드

**API 엔드포인트:**

```typescript
GET / api / rag / analysis / stats; // 필터링 통계 조회
POST / api / rag / analysis / filter; // 필터 조건 적용
POST / api / rag / discovery / execute; // 이슈 발굴 실행 (SSE)
GET / api / rag / discovery / sessions; // 발굴 세션 목록
```

#### 9.2.2 사용자 인터랙션 (`/rag/interaction`)

> **목적**: 발굴된 이슈 검토, 수정, 재발굴 요청, 최종 선택

**주요 기능:**

- 세션 목록 표시 및 선택
- 이슈 카드 목록 (점수, 요약, 키워드, 출처)
- 이슈 선택/제외/편집 기능
- 일괄 선택/해제
- 점수별/클러스터 크기별 정렬
- 중요도 점수 상세 (법적 강제성, 신규성, 파급력, 국제 동향)

**API 엔드포인트:**

```typescript
GET    /api/rag/discovery/sessions/:id              // 세션 상세 조회
PUT    /api/rag/discovery/sessions/:id              // 세션 업데이트
DELETE /api/rag/discovery/sessions/:id              // 세션 삭제
PUT    /api/rag/discovery/sessions/:id/issues/:id   // 이슈 수정
```

#### 9.2.3 심층 분석 (`/rag/deep-analysis`)

> **목적**: 선택된 핵심 이슈에 대한 심층 분석 수행 및 결과 확인

**주요 기능:**

- 선택된 이슈 목록 표시
- 분석 깊이 설정 (빠른/표준/심층)
- 분석 실행 및 진행 상황 표시
- 단계별 분석 결과 펼침 패널
- 분석 방법 수정 및 재분석
- 보고서 내보내기

**분석 단계:**

1. 데이터 수집 (Retrieval)
2. 초기 분석 (Chain-of-Thought)
3. 심층 추론 (Multi-step Reasoning)
4. 결론 도출 (Synthesis)

**API 엔드포인트:**

```typescript
POST /api/rag/analysis/execute          // 전체 분석 실행 (SSE)
POST /api/rag/analysis/execute/:issueId // 특정 이슈 분석
PUT  /api/rag/analysis/:id/revise       // 분석 결과 수정 요청
GET  /api/rag/analysis/:id/export       // 분석 결과 내보내기
```

#### 9.2.4 RAG 설정 (`/rag/settings`)

> **목적**: RAG 시스템 운용에 필요한 모든 설정 통합 관리

**설정 카테고리:**

| 탭            | 설정 항목                                                |
| :------------ | :------------------------------------------------------- |
| **LLM 모델**  | API 키 관리, 모델 선택, 파라미터 (온도, 토큰), 비용 관리 |
| **벡터 검색** | Top-K 결과 수, 유사도 임계값, 메타데이터 필터            |
| **이슈 발굴** | 클러스터링 알고리즘, 최대 이슈 수, 중요도 가중치         |

## 12. RAG 분석 기능 고도화 블루프린트 (Phase 2: Precision & Deep Dive)

> **작성일**: 2026-01-30  
> **목적**: 현재 구현된 기본 RAG 분석 시스템을 '실무형 전문가 도구'로 업그레이드하기 위한 기능 및 UI 고도화 방안

### 12.1 중요도 가중치 시스템 고도화 (Dynamic Scoring & Prompting)

현재 단순히 4개의 고정된 슬라이더를 움직이는 것은 LLM에게 모호한 지시를 내리는 것과 같습니다. 이를 **'동적 평가 기준(Dynamic Criteria)'** 시스템으로 변경해야 합니다.

#### 12.1.1 기능적 요구사항

1. **평가 기준(Criteria)의 동적 관리 (CRUD)**
   - **RAG 설정 메뉴**에서 평가 기준을 사용자가 직접 추가/삭제/수정
   - 예: 기본 4개 외에 `산업계 반발 예상도`, `즉시 시행 여부`, `과태료 부과 여부` 등 추가

2. **기준별 '프롬프트 인젝션' 매핑**
   - 단순히 숫자만 전달하는 것이 아니라, 각 기준이 LLM에게 어떤 의미인지 자연어로 정의

   | 항목 | 설정 예시 |
   |------|----------|
   | **항목명** | 법적 강제성 |
   | **LLM 지침(Prompt)** | "이 이슈가 기업에게 의무를 부과하거나, 위반 시 제재(과태료, 영업정지 등)가 따르는지 평가하십시오." |
   | **가중치 영향** | "이 점수가 높을수록 보고서의 '리스크' 섹션에 우선 배치됩니다." |

3. **가중치 시뮬레이션 (Preview)**
   - 설정 메뉴에서 가중치나 프롬프트를 변경했을 때, 샘플 텍스트에 대해 점수가 어떻게 변하는지 테스트 기능

#### 12.1.2 UI 구현 제안

- **발굴 설정 패널**: 고정된 4개 슬라이더 대신, **'평가 기준 추가'** 버튼(+)이 있는 동적 리스트 형태
- **각 슬라이더 옆 툴팁**: 마우스를 올리면 해당 기준이 LLM에게 어떻게 전달되는지(프롬프트 내용) 팝오버로 표시

#### 12.1.3 평가 기준 데이터 구조

```typescript
interface ScoringCriteria {
  id: string;
  label: string;                    // 화면 표시명
  description: string;              // LLM에 주입될 설명
  examples: {                       // 좋은/나쁜 사례 (프롬프트 품질 향상)
    high: string[];
    low: string[];
  };
  weight: number;                   // 0.0 ~ 1.0
  enabled: boolean;
  calibration?: {                   // 자동 보정(스케일링) 옵션
    minScale: number;
    maxScale: number;
  };
}
```

### 12.4 정밀 발굴을 위한 추가 기능 아이디어

#### 12.4.1 포함/제외 키워드 (Positive/Negative Keywords)

| 기능 | 설명 |
|------|------|
| **Must Include** | 이 단어가 포함된 청크는 가중치를 2배로 부여 |
| **Exclude** | 이 단어가 포함된 청크는 아예 검색/클러스터링에서 배제 |

- **UI**: 태그 입력창 형태 (파란색 태그: 포함 / 빨간색 태그: 제외)

#### 12.4.2 클러스터링 민감도 (Semantic Sensitivity)

| 설정 | 효과 |
|------|------|
| **느슨하게(Broad)** | "탄소중립"이라는 큰 주제로 묶음 |
| **엄격하게(Strict)** | "탄소배출권 가격", "탄소국경세", "RE100"을 모두 다른 이슈로 분리 |

- **UI**: "이슈 응집도" 슬라이더 (Broad <-> Strict)

#### 12.4.3 출처 신뢰도 가중치 (Source Reliability)

- 기관별/게시판별로 중요도 등급(Tier 1, 2, 3)을 매겨 점수 산정 시 반영
- **UI**: 기관 필터 옆에 별점(★)이나 중요도 토글 스위치 배치

#### 12.4.4 관심 기업/물질 엔티티 필터 (Named Entity Filter)

- 특정 기업(예: 삼성전자, SK하이닉스)이나 특정 화학물질에 대한 이슈만 필터링
- 미리 정의된 관심 엔티티 리스트를 선택하여 필터링

## 13. 통합환경허가 사업장 맞춤형 기능 (Client-Specific RAG)

> **목적**: 통합환경허가 대상 사업장(발전, 철강/제철, 화학, 전자, 반도체, 폐기물소각 등)을 주 고객으로 하는 모니터링 보고서 플랫폼에서, 클라이언트의 업종/사업장 규모/적용 대상 법률에 대한 정밀한 매칭 설정

### 13.1 고객 페르소나(Client Persona) 설정

이슈 발굴 전 분석 대상 사업장의 정체성을 명확히 정의. 이 정보는 RAG의 시스템 프롬프트에 주입되어 AI가 문서를 해석하는 관점을 결정합니다.

#### 13.1.1 업종(Industry) 선택 및 공정 태그

| 업종 | 세부 공정 예시 |
|------|---------------|
| **철강/제철** | [소결공정], [코크스공정], [제강공정], [압연공정] |
| **반도체** | [식각공정], [세정공정], [CMP], [유기용제 사용] |
| **발전** | [연소], [탈황], [탈질], [집진] |
| **화학** | [합성], [증류], [건조], [포장] |
| **폐기물소각** | [연소], [배가스처리], [잔재물처리] |

**효과**: "질소산화물(NOx) 저감"이라는 이슈가 발굴되었을 때, 이를 일반적인 내용이 아닌 "소결로 SCR 설비 강화 필요성"으로 해석 가능

#### 13.1.2 사업장 규모 및 입지

| 설정 항목 | 옵션 예시 |
|----------|----------|
| **대기관리권역** | 수도권, 중부권, 남부권, 동남권 등 |
| **사업장 종별** | 1종~5종 |
| **특수지역** | 수질오염총량관리지역, 배출권거래제 대상 등 |

**효과**: 특정 권역에만 적용되는 '대기오염물질 총량관리제' 관련 고시에 해당 권역 사업장에게만 가중치 부여

### 13.3 법적 적용 범위 설정 (Legal Scope Configuration)

#### 13.3.1 적용 법령 매트릭스

| 카테고리 | 법령 예시 | 설정 옵션 |
|----------|----------|----------|
| **통합법** | 환경오염시설의 통합관리에 관한 법률 | 가중치 최상 |
| **매체별 개별법** | 대기환경보전법, 물환경보전법, 폐기물관리법 | 관심/일반/무시 |
| **안전/보건** | 중대재해처벌법, 화학물질관리법 | 관심/일반/무시 |
| **에너지/탄소** | 탄소중립기본법, 배출권거래법 | 관심/일반/무시 |

#### 13.3.2 규제 단계(Regulatory Phase) 필터

```
[입법예고(대응 가능 단계)] → [공포(확정 단계)] → [시행(적용 단계)] → [단속/점검(리스크 단계)]
```

**활용**: 컨설팅 목적상 **'입법예고'** 단계의 문서에 가중치를 두어, 고객사가 의견을 제출하거나 설비를 미리 준비할 수 있도록 유도

### 13.4 컨설팅 로직 (프롬프트·가중치·분석 체인)

#### 13.4.1 BAT(최적가용기법) 기준서 연동 분석

- **RAG 설정**: "BAT 기준서 변경 사항 감지 모드" 활성화
- **로직**: 환경부의 '최적가용기법 기준서' 개정 관련 내용이 나오면, 기존 공정 기술과 비교하여 설비 교체 필요성 분석

#### 13.4.2 리스크 유형별 가중치 (Risk Scoring)

| 리스크 유형 | 설명 |
|------------|------|
| **Cost Impact** | 배출부과금, 과태료, 설비 투자비 증가 요인 |
| **Operation Impact** | 조업 정지, 허가 취소, 공정 가동률 조정 요인 |
| **Admin Impact** | 보고서 제출 주기 변경, 측정 횟수 증가 등 행정 부담 요인 |

## 14. 고객 페르소나 및 컨설팅 로직 보강 (Advanced Features)

### 14.1 "공정/설비-배출구" 수준의 구조화

| 레벨 | 구성요소 | 예시 |
|------|---------|------|
| **설비(Emission Unit)** | 소결로, 보일러, 소각로, 스크러버, SCR 등 | - |
| **배출구(Stack/Outlet)** | 배출구별 오염물질, 배출량, 방지시설, 측정기기 여부 | TMS/자가측정 |

**효과**: 이슈가 "사업장 전체"가 아니라 "특정 배출구/공정"에 직접 매칭되어 대응방안이 구체화됨

### 14.2 "허가조건"과의 매칭

사업장별 통합허가서에 들어가는 **허가조건 항목**을 구조화:
- 모니터링 주기
- 한계배출기준
- BAT-AEL
- 운영조건

법령/고시/기준서 변경이 나오면:
- **허가조건 변경 가능성(High/Med/Low)** 점수화
- **변경 시 필요한 조치** 자동 후보 생성 (측정 주기 변경, 설비 증설, 운영조건 변경)

### 14.3 "규제 성숙도/준수 수준" 프로파일

| 항목 | 설명 |
|------|------|
| 현재 준수 수준 | 여유율/초과이력/개선계획 보유 여부 |
| 최근 행정처분 | 12~24개월 내 개선명령/점검 결과 |

**효과**: 동일한 규제라도 "위험 사업장"에 더 높은 우선순위를 부여

### 14.4 물질 그룹/규제 목록 기반 태깅

단일 물질(CAS)뿐 아니라 **그룹** 단위 설정:
- PFAS군
- 특정수질유해물질군
- VOC군
- 유해대기오염물질(HAPs)

문서에서 물질명이 직접 안 나와도 **동의어/약어/상품명**까지 매칭 (사전/LLM 하이브리드)

### 14.5 단위/기준치 변화 탐지

| 탐지 대상 | 설명 |
|----------|------|
| 단위 변환 | "mg/L→μg/L" |
| 기준 강화/완화 | 수치 변경 |
| 측정방법 변경 | 공정시험 변경 |
| 산정방법 변경 | 배출량 계산식 변경 |

텍스트에서 **수치(숫자), 단위, 대상 공정/시설**을 추출하는 룰+모델 혼합(정규식 + NER)

### 14.6 법령 변경 단계 외 "리스크 유형" 분류

| 유형 | 설명 |
|------|------|
| **의무부과(Compliance)** | 새로운 의무 발생 |
| **보고·공시(Disclosure)** | 공시 의무 변경 |
| **경제수단** | 부과금·배출권 변경 |
| **단속·점검(Enforcement)** | 점검 강화 |
| **지원·인센티브(Subsidy)** | 보조금/지원사업 (투자비 절감 기회) |

### 14.7 '점수'만 말고 "액션(조치)"까지 산출하는 구조

이슈 카드가 다음 구조를 갖도록 설계:

```typescript
interface IssueActionCard {
  obligation: string;      // 무엇을 해야 하는가
  deadline: string;        // 언제까지
  evidence: {              // 근거
    document: string;
    article: string;
    page: number;
  };
  impact: {                // 영향
    cost: "high" | "medium" | "low";
    operation: "high" | "medium" | "low";
    admin: "high" | "medium" | "low";
    reputation: "high" | "medium" | "low";
  };
  actions: {               // 대응
    immediate: string[];
    shortTerm: string[];
    midTerm: string[];
    longTerm: string[];
  };
  owner: string;           // 담당부서 (환경/안전/생산/법무/구매 등 추천)
}
```

### 14.8 업종-규제 지식 그래프 구축

| 구성요소 | 예시 |
|---------|------|
| **노드** | 업종/공정/시설/오염원/물질/법령/고시/허가조건/BAT 항목 |
| **엣지** | "적용된다", "관련된다", "대체/방지시설이다", "측정한다" |

발굴된 문서가 들어오면:
- 그래프에서 **영향 경로(path)**를 찾아 "왜 중요한지" 설명 가능
- 사용자에게 "우리 공장 공정 X → 법령 Y 변경 영향"으로 보여주기 쉬움

### 14.9 리스크 시뮬레이션 (비용/조업/행정)

| 영향 유형 | 추정 항목 |
|----------|----------|
| **설비 투자 CAPEX** | 범주 추정 (정확한 금액이 아니라 등급/범위) |
| **운영비 OPEX** | 약품/전력/폐기물 처리 비용 변화 |
| **행정 부담** | 보고서/측정 빈도/검사 비용 |

"영향도"를 다차원으로 표현: 비용/조업/법적리스크/기간

### 14.10 데이터 품질 & 신뢰성 설정

| 항목 | 설명 |
|------|------|
| **출처 신뢰도** | 법령/고시 원문 > 지침 > 보도자료 > 기사 |
| **문서 버전 관리** | 개정 전/후 비교 |
| **정정/수정본 반영** | 같은 문서의 수정본 추적 |
| **근거 링크/원문 스냅샷** | 감사/보고서 신뢰성을 위한 저장 |

## 15. 사업장 프로파일 시스템 (Site Profile System)

### 15.2 메뉴 배치 제안

#### 안 A (권장): `RAG 분석` 하위에 "사업장 프로파일" 추가

```
RAG 분석
├── 사업장 프로파일 (/rag/profiles)  ← 신규
├── RAG 분석 (/rag/analysis)
├── 사용자 인터랙션 (/rag/interaction)
├── 심층 분석 (/rag/deep-analysis)
└── RAG 설정 (/rag/settings)
```

- 클릭 시 `/rag/profiles`로 이동(또는 모달)

#### 안 B: 독립 메뉴 (확장 시)

```
클라이언트 관리 (/clients)
└── 사업장 관리 (/sites)
```

## 17. RAG 핵심 원리: LLM의 역할과 작동 방식

> **목적**: RAG 아키텍처에서 LLM이 실제로 어떻게 작업을 수행하는지에 대한 정확한 이해

### 17.1 흔한 오해 바로잡기

| 오해 | 실제 |
|------|------|
| LLM이 벡터 DB 전체를 **"학습"**한다 | LLM은 벡터 DB를 **전혀 학습하지 않음** |
| 질문 시마다 DB 전체를 읽는다 | **관련된 소수의 청크만** 검색해서 전달 |
| 막대한 토큰 비용이 발생한다 | 검색된 Top-K 청크만 처리하므로 **저비용** |

**핵심**: LLM은 "검색된 소수의 문서"만 읽고 답변합니다. 벡터 DB 전체를 학습하거나 읽지 않습니다.

### 17.2 RAG 작동 순서 (실제 흐름)

```
┌─────────────────────────────────────────────────────────────────────┐
│                        토큰 소모 비교                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ❌ 만약 DB 전체를 매번 읽는다면:                                    │
│  ────────────────────────────────                                   │
│  400만 청크 × 2,500자 = 100억 자 ≈ 40억 토큰                        │
│  GPT-4o-mini 기준: 40억 × $0.15/1M = $600 (1회 질문당!)             │
│                                                                     │
│  ✅ 실제 RAG (검색 후 상위 K개만):                                   │
│  ──────────────────────────────────                                 │
│  상위 20개 청크 × 2,500자 = 50,000자 ≈ 20,000 토큰                  │
│  GPT-4o-mini 기준: 20,000 × $0.15/1M = $0.003 (1회 질문당!)         │

│  💡 비용 차이: 약 200,000배                                          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 17.4 RAG 핵심 용어 정리

| 용어 | 의미 | 담당 |
|------|------|------|
| **Embedding** | 텍스트를 숫자 벡터로 변환 | 임베딩 모델 (bge-m3 등) |
| **Vector DB** | 벡터를 저장하고 유사도 검색 | ChromaDB/Pinecone |
| **Retrieval** | 질문과 유사한 청크 Top-K 추출 | 벡터 DB 엔진 |
| **Generation** | 검색된 컨텍스트 기반 답변 생성 | LLM (GPT/Claude) |

### 17.5 도서관 비유

```
📚 도서관 비유로 이해하기:

❌ 잘못된 이해:
"사서(LLM)가 도서관의 모든 책을 외운 뒤, 질문에 답한다"

✅ 실제 RAG:
1. 사용자가 "환경 규제"에 대해 질문
2. 검색 시스템이 도서관에서 관련 책 5권을 찾아옴 (Retrieval)
3. 사서(LLM)는 그 5권만 읽고 답변함 (Generation)

→ 사서는 도서관 전체를 외우지 않음
→ 검색 시스템이 관련 자료만 빠르게 찾아줌
```

```
│  💡 검색 시: Level 2 → Level 1 → Level 0 순으로 드릴다운            │
│  💡 토큰 절약: 1000개 청크 → 100개 요약 → 10개 메타요약             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**적용 시점**: 임베딩/인덱싱 단계에서 미리 요약 계층 생성

```
┌─────────────────────────────────────────────────────────────────────┐
│                      Map-Reduce RAG                                  │

│           │                                                         │
│           ▼                                                         │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  MAP 단계: 병렬 처리 (각각 독립적으로 LLM 호출)              │   │
│  │                                                              │   │
│  │  청크 1~50   ──▶ LLM ──▶ 부분 분석 1                         │   │
│  │  청크 51~100 ──▶ LLM ──▶ 부분 분석 2                         │   │
│  │  청크 101~150──▶ LLM ──▶ 부분 분석 3                         │   │
│  │  ...                                                         │   │
│  │  청크 451~500──▶ LLM ──▶ 부분 분석 10                        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│           │                                                         │
│           ▼                                                         │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  REDUCE 단계: 부분 결과 통합                                 │   │
│  │                                                              │   │
│  │  [부분 분석 1~10] ──▶ LLM ──▶ 최종 심층 분석 결과            │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  💡 장점: 병렬 처리로 속도 향상, 컨텍스트 윈도우 한계 우회          │

│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 18.3.1 Hybrid Search (키워드 + 시맨틱 결합)

```
┌─────────────────────────────────────────────────────────────────────┐
│                      Hybrid Search                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  사용자 질문: "NOx 배출허용기준 강화"                                │
│           │                                                         │
│           ├──────────────────────┬──────────────────────┐           │
│           ▼                      ▼                      ▼           │
│  ┌────────────────┐    ┌────────────────┐    ┌────────────────┐    │
│  │ 시맨틱 검색    │    │ 키워드 검색    │    │ 메타데이터     │    │
│  │ (벡터 유사도)  │    │ (BM25/TF-IDF)  │    │ 필터링         │    │
│  │                │    │                │    │                │    │
│  │ "대기오염 저감"│    │ "NOx" 정확히  │    │ law="대기환경  │    │
│  │ "질소산화물"   │    │  포함된 문서   │    │  보전법"       │    │
│  │ 등 유사 개념   │    │                │    │ date>=2025     │    │
│  └───────┬────────┘    └───────┬────────┘    └───────┬────────┘    │
│          │                     │                     │              │
│          └─────────────────────┴─────────────────────┘              │
│                                │                                    │
│                                ▼                                    │
│                    ┌──────────────────────┐                         │
│                    │  Reciprocal Rank     │                         │
│                    │  Fusion (RRF)        │                         │
│                    │  ─────────────────   │                         │
│                    │  가중 합산으로 최종  │                         │
│                    │  순위 결정           │                         │
│                    └──────────────────────┘                         │
│                                                                     │
│  💡 시맨틱만: "질소산화물 관리" 검색 → "탄소중립" 관련 문서 혼입    │
│  💡 키워드만: "NOx" 검색 → "질소산화물"로 표기된 문서 누락          │
│  💡 Hybrid: 둘의 장점 결합                                          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 18.3.2 Re-ranking (2단계 정밀 순위화)

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Re-ranking Pipeline                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Stage 1: 빠른 검색 (Bi-Encoder)                                     │
│  ────────────────────────────────                                   │
│  벡터 DB에서 Top-100 청크 빠르게 추출                                │
│  (코사인 유사도, 밀리초 단위)                                        │
│                                                                     │
│           │                                                         │
│           ▼                                                         │
│                                                                     │
│  Stage 2: 정밀 재순위화 (Cross-Encoder)                              │
│  ──────────────────────────────────────                             │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                                                              │   │
│  │  Cross-Encoder 모델 (예: ms-marco-MiniLM)                   │   │
│  │                                                              │   │
│  │  입력: [질문] + [후보 청크] 쌍으로 직접 비교                 │   │
│  │                                                              │   │
│  │  "NOx 배출기준 강화" + "청크1" → 관련성 점수: 0.92          │   │
│  │  "NOx 배출기준 강화" + "청크2" → 관련성 점수: 0.45          │   │
│  │  "NOx 배출기준 강화" + "청크3" → 관련성 점수: 0.88          │   │
│  │  ...                                                         │   │
│  │                                                              │   │
│  │  → 점수순 재정렬 후 Top-20만 LLM에 전달                      │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  💡 Bi-Encoder: 빠르지만 덜 정확 (독립적 임베딩 비교)               │
│  💡 Cross-Encoder: 느리지만 매우 정확 (쌍으로 직접 비교)            │
│  💡 조합: 1단계에서 후보군 축소 → 2단계에서 정밀 선별               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 18.3.3 Query Decomposition (질문 분해)

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Query Decomposition                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  원본 질문 (복잡):                                                   │
│  "통합허가 대상 철강 사업장의 NOx 배출기준이 강화되면                │
│   어떤 설비 투자가 필요하고, 관련 지원제도는 있는가?"                │
│                                                                     │
│           │                                                         │
│           ▼  LLM이 질문 분해                                        │
│                                                                     │
│  Sub-Q 1: "철강 사업장 NOx 배출허용기준 변경 내역"                   │
│  Sub-Q 2: "NOx 저감 설비 종류와 투자비용"                           │
│  Sub-Q 3: "대기오염방지시설 투자 지원제도"                          │
│  Sub-Q 4: "통합허가 BAT 기준서 NOx 관련 내용"                       │
│                                                                     │
│           │                                                         │
│           ▼  각 Sub-Q로 별도 검색                                   │
│                                                                     │
│  Sub-Q 1 → 검색 → 청크 A1, A2, A3                                   │
│  Sub-Q 2 → 검색 → 청크 B1, B2, B3                                   │
│  Sub-Q 3 → 검색 → 청크 C1, C2                                       │
│  Sub-Q 4 → 검색 → 청크 D1, D2, D3, D4                               │
│                                                                     │
│           │                                                         │
│           ▼  통합하여 LLM에 전달                                    │
│                                                                     │
│  💡 복잡한 질문 하나로 검색 → 관련 없는 결과 다수                    │
│  💡 분해 후 검색 → 각 측면에 정확히 맞는 문서 수집                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 18.3.4 Self-Query (LLM 자가 필터링)

```python
# LLM이 사용자 질문을 분석하여 메타데이터 필터를 자동 생성

사용자: "2025년 이후 환경부에서 발표한 대기 분야 법령안"

LLM 자가 분석 결과:
{
  "semantic_query": "대기오염 관련 법령 개정안",
  "metadata_filter": {
    "published_date": { "$gte": "2025-01-01" },
    "organization": "환경부",
    "sector": "air",
    "doc_type": ["legislation", "notice"]
  }
}

→ 벡터 검색 전에 메타데이터로 후보군을 대폭 축소
→ 관련 없는 문서가 섞일 확률 감소
```

#### 18.3.5 Graph RAG (지식 그래프 결합)

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Graph RAG                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │

│                                                                     │
│  Graph RAG: 엔티티 간 관계를 그래프로 구축                           │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                                                              │   │
│  │     [대기환경보전법]                                         │   │
│  │           │                                                  │   │
│  │           │ 적용                                             │   │
│  │           ▼                                                  │   │
│  │     [NOx 배출기준] ──────────────▶ [SCR 설비]               │   │
│  │           │              필요                │               │   │
│  │           │ 규제                             │ 설치          │   │
│  │           ▼                                  ▼               │   │
│  │     [철강 사업장] ◀──────────────── [BAT 기준서]            │   │
│  │           │              적용대상                            │   │
│  │           │ 해당                                             │   │
│  │           ▼                                                  │   │

│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  검색 로직:                                                         │

│  💡 장점: 유기적 연관성을 구조적으로 보장                           │
│  💡 단점: 그래프 구축 비용, 유지보수 복잡도                         │

└─────────────────────────────────────────────────────────────────────┘
```

### 18.5 기법별 비용 vs 정확도 트레이드오프

| 기법 | 정확도 향상 | 추가 비용 | 권장 상황 |
|------|------------|----------|----------|
| **Hybrid Search** | ⭐⭐ | 거의 없음 | 항상 적용 |
| **Re-ranking** | ⭐⭐⭐ | 낮음 | 항상 적용 |
| **Query Decomposition** | ⭐⭐⭐ | 중간 | 복잡한 질문 |
| **Self-Query** | ⭐⭐ | 낮음 | 메타데이터 풍부 시 |
| **Multi-hop** | ⭐⭐⭐⭐ | 중간 | 심층 분석 |
| **Map-Reduce** | ⭐⭐ | 높음 | 대량 데이터 필수 시 |
| **Hierarchical RAG** | ⭐⭐⭐ | 중간 (사전 구축) | 대규모 DB |
| **Graph RAG** | ⭐⭐⭐⭐⭐ | 높음 (구축비용) | 도메인 특화 |
